The hard part of a large issue isn't the code. It's that the work outlives any one context window. Every session ["begins with a fresh context window"](https://code.claude.com/docs/en/memory), so whatever Claude learned in session one is gone by session four unless it was written somewhere Claude reads back.

The answer I ended up with is one line: `/clear` often, and make sure the code can carry what the context can't. Everything below is how I got there.

I tested this deliberately. An epic of onboarding and demo-data work was handed to Claude Fable 5.1 as a long-running, mostly autonomous task. The code shipped. The process didn't.

## Two ways of keeping the context, both lost it

**Subagents implementing sub-issues.** One long session as coordinator, one subagent per sub-issue. But a subagent ["returns only the summary"](https://code.claude.com/docs/en/sub-agents), and one that misunderstood the task and one that got it right both return a confident summary. The coordinator can't tell them apart and builds on both. That's fine for research and review, where a short answer is the goal. Not for building, which the docs keep in the main conversation because "multiple phases share significant context, such as planning, implementation, and testing".

**One sub-issue per step.** Seven sub-issues, one session each, GitHub as the memory. All seven shipped, in four PRs. What didn't ship was confidence in the design. A one-commit change arrived with a rewritten issue, a full PR description and a review round, and every finding that mattered got written into the parent issue instead of the sub-issue it belonged to. Nobody read them, nothing was decided in them, and the four PRs would have shipped the same without them.

The docs never suggest sub-issues. They suggest one spec, ["write a complete spec to SPEC.md"](https://code.claude.com/docs/en/best-practices#let-claude-interview-you), then a fresh session to execute it.

## The finding

The parent issue as living spec — tables for steps, decisions and findings, updated every session — Claude kept perfectly. I couldn't follow them. The prose around the change outgrew the change, and when I finally wanted to know what the demo-data feature did, I read the code and understood it in a fraction of the time.

The code is the only artifact both of us read the same way. Everything else — issue, PR body, transcript — is scaffolding for one party's memory. `CLAUDE.md` should exclude ["information that changes frequently"](https://code.claude.com/docs/en/best-practices#write-an-effective-claude-md) and compaction eats the transcript, so the tracker was the one place left, and it filled up.

## What follows

**Claude forgets at the end of every session**, and a long one degrades well before it ends: "a clean session with a better prompt almost always outperforms a long session with accumulated corrections." So don't defend the context, discard it. `/clear` between every piece and after the second correction, with the durable memory being the code plus one short plan.

**Claude keeps producing at the same confidence** where a tired human slows down and says so. That's the docs' trust-then-verify gap, "a plausible-looking implementation that doesn't handle edge cases". So the unit of delegation is one PR you'll actually read, and nothing writes to the tracker from a polluted context.

**Claude fills gaps with output where a human fills them with judgment.** Two halves, and only one is a planning problem. How much code fills a gap is a per-edit habit that a skill like [ponytail](https://github.com/dietrichgebert/ponytail) trims. Whether the gap should be filled at all is planning: ["explore first, then plan, then code"](https://code.claude.com/docs/en/best-practices#explore-first-then-plan-then-code), starting in plan mode, which is [never triggered for you](https://code.claude.com/docs/en/permission-modes#skip-all-checks-with-bypasspermissions-mode). The plan also fixes the order — scripts, schema, helpers and fixtures land first with no business meaning, then the feature goes in as one PR of pure logic. Mixing them is what made the epic unreviewable: a helper, a schema and a behaviour in one diff is three unrelated questions at once.

## The record is the diff

Clearing often is only cheap when nothing valuable is lost with the context, and that is the whole design: keep the plan short, keep the PRs small, and let the code be the record. Everything written about the code should stay smaller than the code.

The [architect skill](/skills/architect) that accompanies this post makes Claude work that way by default, and for anything vague the companion [interview skill](/skills/interview) runs first, writing a self-contained `SPEC.md` for a fresh session. From there a run goes: read the code and the nearest similar feature, name the pattern to follow; write one plan file readable in a minute, slices in order, tooling before feature, open questions for the human; open the tooling PR, then the feature PR, each with one test per behaviour and a one-paragraph body; delete the plan file and move any convention worth keeping into `CLAUDE.md`. Each step starts from `/clear`. No sub-issues, no findings comments, no follow-ups filed.

## The one rule that went into CLAUDE.md

Skills load when they trigger. One rule was worth loading in every session, so it lives in the global `~/.claude/CLAUDE.md`:

> Never create GitHub sub-issues, and never treat sub-issues as tasks for subagents. A sub-issue is tracker bookkeeping, not a unit of work: handing one to a subagent returns a summary that hides whether the task was understood, and the coordinator cannot tell a misread from a correct one. Subagents do research and review a diff in a fresh context; they do not implement. Work is split into PRs, not issues, each implemented in the main session and read by a human before the next one starts. If a step needs a home, it goes in the plan file (see the architect skill). Open a separate issue only when the user explicitly asks for one or a different person will pick it up.

It carries its reason, which the docs say matters more than emphasis. Nothing in it is a product fact; it is a statement about where work is allowed to live.
